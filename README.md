# ci-jenkins

Jenkins shared library for projects generated by `action-platform`. Logic lives in [ci-scripts](https://github.com/actionplatform/ci-scripts); every step fetches it at `v1`.

No Jenkins configuration needed — load it from the Jenkinsfile:

```groovy
library identifier: 'ci-jenkins@v1',
        retriever: modernSCM([$class: 'GitSCMSource',
                              remote: 'https://github.com/actionplatform/ci-jenkins.git'])

apPipeline(image: 'python:3.12')
```

Or register it once (Manage Jenkins → Global Pipeline Libraries → name `ci-jenkins`, this repo, default version `v1`) and use `@Library('ci-jenkins@v1') _`.

Needs a Docker-capable agent and a Multibranch job for the PR-only stages. Set `AP_SCRIPTS` (job or global env) to point every step at a fork of ci-scripts.

| Step | Does |
|------|------|
| `apSetup(language:)` | dependencies |
| `apCheck(language:)` | lint, format, tests |
| `apConventionalCommit(base:)` | Conventional Commits on the change range |
| `apGitflow(head:, base:)` | branch name and merge target follow git-flow |
| `apRelease(tag:, files:, branch:)` | version bump from tag |
| `apPipeline(image:, language:)` | declarative pipeline: setup → check → commits → git-flow (PRs) |

## Deploy jobs the platform starts

A deploy job of your own (not `apPipeline`) can be started from Action Platform: declare it in `platform.toml` as a target with `run_by = "jenkins"`, `observe = false`, its `job` path and `version_parameter` — the job's string parameter that receives the release tag (`RELEASE_TAG`, say). The platform calls `buildWithParameters` with that parameter alone, follows the build through the queue and its stages, and records the result. The job keeps its own credentials; the platform's Jenkins user needs *Overall/Read* and *Job/Read* + *Job/Build* on that job. The model: [deployments](https://github.com/actionplatform/action-platform/blob/master/docs/concept_deployments.md#dispatched-jenkins-jobs).

Tag `vX.Y.Z`; `v1` floats to the latest.
